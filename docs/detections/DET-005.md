# DET-005 — RDP logon from a source outside the documented jump hosts

> Status: **fixture-validated** (2026-08-29). Compiled query proven on a live Elasticsearch 8.19.20
> against synthetic fixtures. Not yet run against telemetry generated on a real host.
> CrowdStrike LogScale: **not compiled** — the pySigma Falcon pipeline has no Windows Security
> 4624 mapping (`detections/compiled/manifest.json`).

## Objective

In an environment with a documented RDP path (jump hosts), a successful RemoteInteractive logon
from anywhere else is either a policy violation or lateral movement. The rule is intentionally
simple; its entire tuning surface is the jump-host list.

## ATT&CK mapping

- Technique: T1021.001 — Remote Services: Remote Desktop Protocol
- Authoritative URL: <https://attack.mitre.org/techniques/T1021/001/>
- Version/access date: Enterprise ATT&CK v19.2, accessed 2026-08-29
- Mapping rationale: detects the successful use of RDP for lateral movement on the *target* host;
  it does not detect RDP configuration changes (Atomic tests 2–4), which belong to T1021.001's
  enabling steps and need registry telemetry.

## Data requirements

- Sensor and configuration: Windows Security auditing with Logon events enabled (4624), shipped
  through the Elastic Windows integration.
- Event IDs/categories: Security 4624 (`winlog.channel: Security`, `event.code: 4624`).
- Required fields: `winlog.event_data.LogonType`, `source.ip`.
- Known collection gaps: Winlogbeat drops an `IpAddress` of `-` before it reaches `source.ip`, so
  console logons have no source address at all (negative control 2). NLA produces a LogonType 3
  pre-authentication event first; the rule ignores it and waits for the type 10.

## Detection logic

1. `event.code` is 4624 and `LogonType` is 10 (RemoteInteractive), **and**
2. `source.ip` is **not** one of the jump hosts (`10.10.20.5`, `10.10.20.6`) or loopback
   (`127.0.0.1`, `::1`).

The Sigma source has no `-` in the filter on purpose: it never reaches ECS, and a `-` term against an
`ip`-typed field would break the query.

## Validation

- Positive fixture: `FIX-DET-005-POS` — 2 events (RDP from the workstation subnet, RDP from a VPN
  pool address). Shape follows Atomic Red Team T1021.001 test 1 as seen on the target.
- Negative control: `FIX-DET-005-NEG` — 3 events (RDP from a jump host, a console logon with no
  source address, a type-3 network logon from the same workstation address).
- Source telemetry fixture: `tests/fixtures/telemetry/DET-005/`.
- SIEM alert evidence: `test_query_returns_exactly_its_own_positives[DET-005]` — 2 of 2 positives,

## False positives and tuning

Researched:

- Help-desk staff connecting directly from workstations where no jump-host policy is enforced. The
  fix is the policy; until then the rule is a policy monitor, not an intrusion alert.
- VDI brokers, monitoring appliances and backup servers that open RDP sessions — add them to the
  filter with a change record.

Observed: none — no production telemetry has been run through this rule.

## Triage guidance

1. Identify the source: is it a workstation, a server, or an address outside the estate?
2. Correlate with the source host's own events: a 4648 (explicit credential use) or a 4624 type 10
   chain across several hosts within minutes is the lateral-movement pattern.
3. Confirm with the account owner; a successful logon with a service account is an immediate
   escalation.

## Blind spots

- Restricted Admin mode and some RDP wrappers produce different logon types; the rule only sees
  type 10.
- If the jump-host list drifts from reality (new jump host added without a rule change), every
  session from it fires — the failure mode is noise, not silence, which is the safer direction.
- RDP over a non-standard port is invisible here (this is a logon rule, not a network rule); the
  network-connection variant to port 3389 is a different detection.

## Hunt note

- Hypothesis: successful RDP logons form a small, stable source→destination graph per environment.
- Query: 4624 type 10 grouped by (`source.ip`, `host.name`, `user.name`), 30 days, first-seen edges.
- Benign noise expected: admins from jump hosts, VDI brokers.
- Signal: a workstation-to-workstation edge, or a service account with an interactive RDP session.
- Follow-up: every stable benign edge that is not a jump host is a policy question for the owner.
